## What was *not* done

Real reviewer-labeling pass against `examples/oasis-core-scan/`. The plan
called for re-labeling that example under the new vocabulary to validate
the link end-to-end on real audit data. Three issues blocked that:

1. **`examples/oasis-core-scan/` ships only `REPORT.md`.** No
   `07_arbiter/findings.json`, no memos, no hypotheses, no
   `ExpertCitationValidation` entries. `teecheck review` and
   `teecheck stats` cannot run against it as-is.
2. **No `runs/oasis-core-*` exists locally.** Every run dir under
   `tee-usage-scanner/runs/` targets either `oasis-sdk`, `relic`, or
   `secret-network` — not `oasis-core`.
3. **Synthesizing artifacts from REPORT.md is not real dogfood.** It
   exercises the wire format (which the C5 snapshot test now covers
   anyway) but doesn't test the citation-validity discriminator on
   real source code, and "have I labeled scanner output that I can
   reproduce" is a different claim from "the schema/code logic is
   self-consistent".

## Acceptance criteria for the future real run

When real dogfood happens, the run is "successful" iff:

1. `teecheck review` writes valid Phase 1.5 records to
   `08_review/review_records.jsonl` for at least 5 findings.
2. `teecheck stats <run-dir>` outputs all three rates with
   non-zero denominators.
3. `by_citation_validity` shows ≥2 distinct buckets (otherwise the
   discriminator hasn't been exercised).
4. At least one finding receives `false_positive +
   outer_validation_missed` (or the actual taxonomy code that fits
   the case — could be `protocol_semantics_missed` etc.; the
   important thing is that `reason_codes` has ≥1 distinct entry).
5. The fixture in `TestCollect_Review_OasisCoreFixture_JSONSnapshot`
   gets reviewed against the real labels. If they diverge
   meaningfully, the fixture is updated to match observed reality.
